I found a real source-level explanation for the recovery storm, and it appears to be a regression from the recent recovery-lifecycle work. I audited current `master` at `05663843`; CI is green, so these are lifecycle/interaction gaps the test suite currently misses.

- **P0/P1 — the “click Recover/Discard 100 times” bug is real, and commit `8a63b710` is the likely origin.** Recovery retirement was moved off the UI thread into a detached task in `crates/chaus-editor/src/editor_recovery.rs:37-58`. Normal clean close, discard, save-and-close, `:q`, etc. can schedule deletion and then immediately destroy the window/process. On the last window, `crates/chaus-app/src/app.rs:183-189` calls `cx.quit()` without waiting for pending recovery cleanup. That means the process can exit before the `.rec` file is removed. On next launch, `crates/chaus-io/src/recovery.rs:225+` blindly reads **every valid recovery file**, and `app.rs:237-248` queues all of them. `discard_next()` removes exactly one at a time (`editor_recovery.rs:295-301`), producing the absurd click-through behavior. The test added for this work, `tests/recovery_lifecycle.rs`, proves retirement is nonblocking, but never tests closing the final window while retirement is still pending. Closed issue #46 therefore fixed the UI-blocking problem but introduced an application-shutdown durability hole.

- **P0 — delayed startup recovery can overwrite brand-new work.** Chaus deliberately scans recovery files asynchronously (`app.rs:193-195`). With no command-line file, it opens an untitled recovery host before that scan completes. If you start typing while a large recovery backlog is being read, the eventual result is unconditionally passed to `queue_recovery()` (`app.rs:230-248`). There is no `document.is_dirty()` guard in `editor_recovery.rs:111+`. Clicking Recover then calls `document.reset(...)` in `recover_next()` and replaces what you just typed. Recovery results should use the initial window only while it is still pristine; otherwise Chaus needs to open a separate recovery window.

- **P1 — recovery handling itself makes a backlog much worse.** `list_in()` has no age/staleness pruning, no deduplication, and no comparison with the current saved file. Escape calls `dismiss_recovery()` at `editor_recovery.rs:313-316`, which merely clears the in-memory queue: every snapshot comes back next launch. Recovering one record deliberately clears the remaining queue while leaving those files on disk, so they also come back next time. The prompt only shows `record.display_name()`, which is just the basename (`recovery.rs:129-134`), making ten recoveries named `README.md` impossible to distinguish. There is also no **Discard All**. This explains why a small cleanup leak eventually becomes a ridiculous user-facing failure.

- **P1 — recovery startup is potentially very expensive once the leak happens.** Individual records can be up to **64 MiB** (`recovery.rs:19`). `list_in()` calls `fs::read()` and fully decodes every valid record before returning (`recovery.rs:225-258`), with no aggregate memory/I/O limit. One hundred leaked snapshots can therefore turn startup into a substantial disk/memory operation. That also widens the dirty-startup-window race above. Recovery discovery should be metadata/header-first and lazily load the selected document body.

- **P1 — recovered files can silently lose their BOM and original Save As suggestion.** `recover_next()` correctly stores `record.original_path` and `record.had_utf8_bom`, then deliberately sets `self.file = None`. But `save_as_inner()` in `editor_file.rs:287-294` gets the suggested filename and BOM state exclusively from `self.file`. For a recovered document, that therefore becomes “no suggested original path” and `had_utf8_bom = false`. A recovered UTF-8-BOM document saved again via Save As can lose its BOM. Those recovery fields already exist; Save As simply isn't consulting them.

- **P1 — the external-file watcher can permanently wedge.** The periodic watcher marks `disk_check_in_flight = true` in `editor_watch.rs:113-116`. When its background result arrives, it checks `disk_epoch`; at `:132-134`, a stale epoch causes an immediate return. The code that actually clears `disk_check_in_flight` is later, in `apply_disk_check()` at `:187`. A save/reload during a disk check can therefore leave the flag permanently true. From then on, periodic checks and manual checks can believe a check is already underway forever, so external edits stop being noticed. `tests/watch_scheduling.rs` tests normal completion, but not an epoch change while a check is running.

- **P1 — Save-conflict resolution loses “I was trying to close” state.** Suppose you close a dirty document, choose Save, and Chaus detects an external modification. `editor_file.rs:609-616` opens the conflict sheet while retaining `close_prompt`. But the conflict actions throw away the original close intent: Reload calls ordinary `open_path()`, Save As uses `CloseAfter::No` (`editor_conflict.rs:70-72`), and Overwrite uses `save_inner(CloseAfter::No)` (`:75-78`). Consequently, resolving the conflict can leave the old close sheet behind or require another close/save cycle. `:wq` is worse: its `CloseAfter::Ex` intent is simply lost after the conflict. The existing conflict and close tests exercise these two state machines separately, which is why this slipped through.

- **P2 — Replace skips the match you are looking at.** `replace_one()` starts its search at `self.selection.range().end` (`editor_find.rs:117-132`). After Find Next selects a match, pressing Replace therefore searches *after* that selection and replaces the following match instead of the current one. It should first test whether the current selection equals the search term and replace that selection; only otherwise search forward. `tests/find_bar.rs` has Find Next and Replace All coverage, but no Replace One test.

- **P2 — Tab in plain Find can put keyboard focus into an invisible field.** `find_bar_key()` at `editor_find.rs:219-241` always alternates between the Find and Replace `TextField` entities. But ordinary Find renders no Replace row. Pressing Tab while using Find can therefore focus a TextField that isn't visible, making typing/focus appear broken. The Tab order needs to be based on `show_replace`.

- **P2 — wrapped-line mouse hit testing has a missing clamp.** `editor_pointer.rs:114-127` determines the visual row and its `span`, then computes the click as `span.start + local_columns`. It never clamps this to `span.end`. With word wrapping, a visual row may end well before the right edge of the window. Clicking blank space to the right of that row can therefore resolve to characters belonging to the **next visual row** of the same logical line. The keyboard equivalent in `move_caret_to_row()` does correctly clamp to `span.end`, which makes the pointer omission fairly clear. This can manifest as seemingly random caret/selection jumps near wrapped lines.

- **P2 — Vim path completion lies in very large directories.** `editor_completion.rs` scans at most `4096` raw directory entries and retains at most `256` matches. The bounded scan is sensible, but when zero matches are found it unconditionally reports `"No matching files"` at `:129-134`, even if `Listing::truncated` is true. A matching file after entry 4096 therefore exists but Chaus explicitly tells you it doesn't. The result should distinguish “no match” from “scan truncated before finding one.”

- **P3 — horizontal scrolling can disappear arbitrarily far into blank space.** In no-wrap mode, wheel/trackpad horizontal deltas directly modify `scroll_x` (`editor_pointer.rs:98-105`). `clamp_scroll()` only clamps it to `>= 0` (`editor.rs:903-906`); there is no right-hand maximum. Repeated horizontal scrolling can move all document text completely offscreen until caret movement happens to pull the viewport back. Drag-selection autoscroll has a separate quirk: it moves one row only in response to mouse-move events (`editor_pointer.rs:49-80`), so holding the pointer stationary outside the viewport does not continue scrolling like a normal editor.

There is one more recovery edge case worth hardening: `list_in()` accepts any correctly encoded `recovery-*.rec` file but doesn't verify that the ID encoded in the filename matches `RecoveryRecord.id`. Discard later deletes the canonical filename generated from the **embedded ID**, not necessarily the file it loaded. A copied/renamed recovery file can consequently become a “ghost” that returns forever. Low probability, but trivial to prevent.

The recovery problem should be fixed first as a single coherent subsystem change: keep retirement asynchronous during normal use, but introduce an application-owned recovery operation queue with a **final shutdown drain**, just as Chaus already explicitly flushes its settings writer before quitting. Then harden startup recovery against dirty host windows, add bulk cleanup/deduplication, preserve recovered path/BOM metadata, and add a deterministic “retirement blocked while last window closes” regression test. I would address the disk-watcher wedge and close/conflict state loss immediately after that; those are the other two state-machine bugs most likely to cause confusing real-world behavior.

For your current installation, the Windows recovery store is `%LOCALAPPDATA%\Chaus\Recovery`. The pile of `.rec` files there should correlate directly with the number of prompts you're seeing. I would **back that directory up before cleaning it**, because some entries may contain genuinely unsaved work.
